- feat(acts): parallel containers gain a join rule, and steps gain input validations. `Step::join` decides how a container whose children run together continues: `all` (the default — every child settles and a child failure fails the chain, the engine's original shape), `any` (the first completion decides), `partial(n)`/`partial(p%)` (a threshold of completions — `partial(1)` is `any` and `partial(100%)` is `all` by the arithmetic alone), or `{ action, params }`, where the engine asks the client instead: one `acts.core.join` request per child settlement, carrying the rule's params and the children's outcomes census (`{node, generation, state, outputs}` each — a client's string inputs decode as literal text, the way the engine reads them, instead of being dropped), answered `complete` (the container passes), `fail` (it fails with the answer's own error) or `skip` (defer — the next settlement asks again, and an idle container re-asks once). `acts.core.block{ mode: parallel }` and `acts.core.parallel` take the rule in their params (the import copies it onto the container step — for `parallel{ in }` the parallel step itself, whose children are the per-item templates); a step that declares its own `branches` uses the same field, while a rule on a sequential shape, with an explicit `next`, or in a form that does not parse is refused at `Workflow::valid()`. A threshold rule completes its container early and withdraws the children still in flight (`SkipTask`), so the run record closes clean instead of parking strays under a decided container; it fails the container once the threshold can no longer be reached, and a count above the real children fails loudly at the fan-out (the dynamic `in` items included). The error walk now stops at the nearest join container that tolerates failure (`any`/`partial`/`action`): a failed vote is one non-completion in that container's census instead of its death, while `all` and every rule-less chain keep the legacy walk. Guard-skipped branches and client-removed acts were never in the vote (not counted), and an aborted child still aborts the chain. Separately, `Step::rules` validates a step's inputs when its act starts — after the vars and resolved params are known, before the act announces itself to a client: each rule is `{ if, message? }` (a bare expression string is the shorthand without a custom message), decided against the step's scope with the resolved params on top (the act's parameters answer by name). A violated rule fails the step with `error.code = "validation_failed"` and the rule's message — catchable through `catches` like any other failure. `README.md` documents both, and `examples/approve` demonstrates `all`, `any` and the delegated `action` (a chair/deputy countersign the client answers through the `acts.core.join` requests).

- refactor(acts): the scheduler shell's split modules are wired in, and the store-facing timers are the kernel host's own serve ticks. `shell/mod.rs` shrinks from 3993 to ~2300 lines: `admission`, `delivery`, `lifecycle`, `liveness`, `recovery`, `snapshot` and `timers` are declared submodules now (their previously inline twins are deleted; the extracts were verbatim lifts, so this is a move), the shared health module moves to `scheduler::core::health` (the deterministic core now owns `LoopGuard`/`SchedulerHealth`/`KernelSchedule`/`TimerGuards`/the metrics gauges; `shell::health` and the duplicated metric structs in both `shell/mod.rs` and `runtime.rs` are gone), and `SnapshotRegistry` lives with the shell instead of the runtime. The four store-facing timers (schedule triggers, message retries, terminal cleanup, snapshot TTL purge) no longer spawn their own tasks: `TimerGuider` exposes one `*_tick` pass each, `KernelSchedule` carries their four intervals, and `KernelHost::serve` ticks them from the same `select!` that drives ready/recovery/outbox/projection — one background task, one store-touching service, so a timer pass can never run concurrently with another background pass or delay an operation out of band. `Runtime`'s `init_retry_timer`/`init_cleanup_timer`/`init_trigger_timer`/`init_snapshot_timer` (and the interval/schedule helpers behind them) are deleted: `Runtime::create` attaches the guider to the host, the kernel host owns `TimerGuards` — the single timer-health state its `scheduler_health` reads — `Runtime::scheduler_health`/`cleanup_metrics` delegate to it, `Runtime` keeps only the pid-lane router and write-behind writer the cleanup pass needs, and `Engine::start`'s boot section no longer starts anything. The cleanup loop keeps its test contract (a no-op under `cfg(test)`; the reliability cells drive `Runtime::sweep_removable` explicitly), and the timer suite drives each pass directly, pinning that one tick is one pass.
